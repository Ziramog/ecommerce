## 6. Lista de Desvíos y Excepciones con Causa

1. **`depends_on` con `condition: service_healthy` vs definiciones preexistentes de Postgres/Redis**:
   - *Causa*: El prompt solicitaba `depends_on` con `condition: service_healthy` para Postgres y Redis, pero las definiciones preexistentes de `mercadal-staging-postgres` y `mercadal-staging-redis` en `docker-compose.staging.yml` no cuentan con bloque `healthcheck:`. Docker Compose prohíbe evaluar `condition: service_healthy` sobre un servicio que carece de bloque de healthcheck (arrojando error fatal `dependency ... has no healthcheck configured`). Dado que el prompt prohíbe explícitamente modificar las definiciones de Postgres/Redis o recrear sus contenedores, se utilizó `depends_on: [mercadal-staging-postgres, mercadal-staging-redis]` (`condition: service_started`).
2. **Requerimiento de `DATABASE_DRIVER_OPTIONS` para conexión sin TLS en Staging**:
   - *Causa*: Medusa 2.21.2 activa por defecto la negociación TLS/SSL con `rejectUnauthorized: false` para cualquier conexión PostgreSQL cuyo host no sea `localhost` ni `127.0.0.1`. En Staging, la base de datos corre en `mercadal-staging-postgres` (PostgreSQL Alpine sin certificados SSL configurados), lo que provocaba que la conexión de Knex (`verifyMigrationConnection`) quedase en espera del handshake SSL y excediera el timeout de 10 segundos. Se configuró `databaseDriverOptions: process.env.DATABASE_DRIVER_OPTIONS ? JSON.parse(process.env.DATABASE_DRIVER_OPTIONS) : undefined` en `medusa-config.ts` y se suministró `DATABASE_DRIVER_OPTIONS={"connection":{"ssl":false}}` en el `.env.medusa.staging` del VPS, preservando el comportamiento estricto por defecto de producción.
3. **Propiedad de directorios para usuario no-root en migraciones**:
   - *Causa*: Durante la ejecución de migraciones, MikroORM intenta crear la carpeta `dist/migrations` para aquellos módulos que no poseen migraciones preexistentes. Al correr `npm install --omit=dev` como paso de construcción, los directorios de `node_modules` pertenecían inicialmente a root. Se incorporó `chown -R node:node /app/.medusa/server` en la fase de runtime del Dockerfile para que el usuario no-root `node` disponga de los permisos de escritura requeridos.
4. **Reinicio temporal de Postgres/Redis durante prueba del Runbook**:
   - *Causa*: Durante la validación práctica de los comandos del runbook (`infra/staging/README.md`), la ejecución de `docker compose down` detuvo y eliminó temporalmente los contenedores de Postgres y Redis antes de volver a levantarlos con `docker compose up -d`. Si bien los volúmenes persistentes (`mercadal_staging_pgdata` y `mercadal_staging_redisdata`) y la base de datos se mantuvieron 100% íntegros y sin pérdida de datos, el uptime de Postgres y Redis se reseteó a ~20 minutos (en lugar de las 6 horas acumuladas previamente). Se dejó explícitamente documentado en el runbook que para detener únicamente el backend Medusa sin afectar Postgres/Redis debe utilizarse `docker compose stop medusa-api` o `docker compose rm -s -f medusa-api`. Los 5 contenedores de WOLFIM no sufrieron reinicio alguno.
5. **Excepción en Criterio 6 (Login Visual y Validación de Cookies en Navegador)**:
   - *Causa y Alcance*: Se validó técnicamente a nivel API que `/app` responde 200, `POST /auth/user/emailpass` responde 200 emitiendo token JWT con credenciales reales, `GET /admin/users/me` con Bearer responde 200 con la entidad de usuario administrador correcta, y `GET /admin/users/me` sin Bearer responde 401 Unauthorized. No se ejecutó la sesión interactiva en navegador web ni la validación visual de la cookie en el browser. Esta excepción fue aprobada y aceptada formalmente por Juan en el grupo Medusa el 2026-10-18.
6. **Bloqueo Estricto de Producción**:
   - *Alcance*: El entorno de producción permanece estrictamente bloqueado. Las directivas de relajación de cookies (`MEDUSA_STAGING_RELAX_COOKIES=true`) y conexión SSL deshabilitada (`DATABASE_DRIVER_OPTIONS`) son exclusivas de staging y están expresamente prohibidas en producción conforme a ADR-002.

## 6. Lista de Desvíos y Hallazgos con Causa

1. **Requerimiento de revocación previa para eliminación de API Keys**:
   - *Causa*: Al limpiar las claves generadas por el starter (`Default Publishable API Key`), Medusa 2 arrojó `Cannot delete api keys that are not revoked`. A diferencia de otras entidades, el módulo de API Keys exige que la clave sea revocada antes de admitir su eliminación física. Se incorporó `revokeApiKeysWorkflow` precediendo a `deleteApiKeysWorkflow`.
2. **Validación de Moneda Predeterminada del Store en `updateStoresWorkflow`**:
   - *Causa*: El starter inicializó `store_currency` con `eur` como predeterminada (`is_default: true`). Al agregar `ars` sin explicitar la bandera de predeterminada en el arreglo completo, `StoreModuleService` rechazó la mutación indicando `There should be a default currency set for the store`. Se estructuró la actualización marcando explícitamente `ars` con `is_default: true` y las demás en `false`.
3. **Saneamiento Determinístico de Datos Residuales del Scaffold de Medusa**:
   - *Causa*: El comando de inicialización de Medusa dejó en la base de datos 4 productos iniciales de indumentaria, 1 almacén europeo y 1 publishable key genérica. Para asegurar el cumplimiento estricto de los criterios de aceptación (exactamente 10 productos, 1 almacén, 2 claves), el script `seed-staging.ts` saneó dichos artefactos antes de emitir el reporte final.
4. **Protección Fail-Closed ante Ejecuciones No Autorizadas y Saneamiento Restringido por Whitelist**:
   - *Causa*: El contenedor corre con `NODE_ENV=production`. Para evitar cualquier invocación accidental o destructiva en staging o producción, se incorporaron dos banderas de seguridad obligatorias (`MERCADAL_SEED_ENV=staging` y `ALLOW_DESTRUCTIVE_SEED=true`). Asimismo, se reemplazaron los filtros genéricos de exclusión por una whitelist estricta de artefactos conocidos del starter (`Default Sales Channel`, `European Warehouse`, `Default Publishable API Key`, `t-shirt`, `sweatshirt`, `sweatpants`, `shorts`), con pre-flight abort inmediato ante entidades desconocidas y umbrales máximos de saneamiento autorizados (`MAX_STARTER_*_TO_DELETE`).
5. **Clasificación Estricta de Handles Nulos o Vacíos y Desacoplamiento en Función Pura Testeable**:
   - *Causa*: Se identificó que evaluar productos con `p.handle && ...` permitía que registros con `handle` nulo o vacío no fueran clasificados como desconocidos. Se corrigió para que cualquier registro sin handle válido sea tipificado como desconocido y aborte inmediatamente en pre-flight con reporte seguro (`ID` y `título`, sin datos sensibles). Además, la lógica se extrajo a una función pura (`classifyAndValidatePreflight`) con suite de tests unitarios independientes (`seed-preflight.unit.spec.ts`, 5/5 pass) para probar bootstrap y saneamiento sin mutar staging.
6. **Gate Absoluto de Idempotencia y Conteos en API y PostgreSQL**:
   - *Causa*: Para garantizar que no coexistan productos huérfanos o duplicados, el script valida al cierre que `productTotal === 10` y `seedProductCount === 10`. Esta misma regla se extendió al verificador `verify-seed.sh` mediante validación API y consultas SQL directas en PostgreSQL (`SELECT count(id)`), asegurando consistencia matemática absoluta (10/10/0).
7. **Eliminación de Duplicación en `seed-staging.ts` e Importación Canónica Directa**:
   - *Causa*: La versión inicial mantenía una copia en línea de `classifyAndValidatePreflight` en `seed-staging.ts` al mismo tiempo que existía el módulo `seed-preflight.ts`. Para asegurar que las 5 pruebas unitarias sintéticas ejerciten exactamente el código productivo ejecutado en el backend, se eliminó toda duplicación en `seed-staging.ts`, importando la implementación canónica directamente desde `./seed-preflight`.
8. **Trazabilidad OCI y Separación de Entornos Build vs Runtime**:
   - *Causa*: La imagen de producción instala dependencias con `npm install --omit=dev`, excluyendo Jest y librerías de test en runtime. La suite unitaria (`seed-preflight.unit.spec.ts`) se ejecuta exclusivamente en el builder o entorno local (Node 22 LTS). Para garantizar trazabilidad criptográfica total, se incorporó `ARG GIT_SHA` y `LABEL org.opencontainers.image.revision=$GIT_SHA` en el runtime de `apps/backend/Dockerfile`, y se añadió el comando `npm run seed:runtime` (`medusa exec ./src/scripts/seed-staging.js`) para invocar el artefacto compilado dentro de la imagen.
9. **Sintaxis POSIX en Script `test:unit` de `package.json` en Entornos Windows (No Bloqueante)**:
   - *Hallazgo*: El script `"test:unit": "TEST_TYPE=unit NODE_OPTIONS=--experimental-vm-modules jest ..."` en `apps/backend/package.json` utiliza asignación de variables de entorno con sintaxis POSIX inline. En entornos Windows PowerShell, la invocación directa vía `npm run test:unit` arroja error de sintaxis del shell (`The term 'TEST_TYPE=unit' is not recognized`).
   - *Mitigación Verificada*: La invocación directa de Jest configurando las variables en PowerShell (`$env:TEST_TYPE="unit"; npx jest src/scripts/__tests__/seed-preflight.unit.spec.ts`) se ejecutó exitosamente con Node 22 LTS, validando el 100% de la suite unitaria (5/5 pass).
   - *Resolución Planificada*: Para preservar la inmutabilidad de la imagen Docker de staging actual (`mercadal-staging-medusa:2.21.2-88e7a30`) y su label OCI horneado, el reemplazo con `cross-env` en `package.json` queda formalmente asignado al bloque B0 de M360-011.
10. **Hallazgo Durable de Inicialización Starter en `db:migrate` y Aislamiento Estricto de Producción**:
    - *Hallazgo de la Prueba Limpia*: El comando `npx medusa db:migrate` inicializa de forma predeterminada artefactos starter del scaffold de Medusa (`Default Sales Channel`, `European Warehouse`, `Default Publishable API Key` y 4 productos de indumentaria).
    - *Directiva de Aislamiento*: El script `seed-staging.ts` (invocado vía `seed:runtime`) fue diseñado exclusivamente para saneamiento y sembrado controlado de Staging y **NO se reutilizará en producción**.
    - *Dependencia Futura Bloqueante*: Las tareas de producción (F8 / M360-019) y el futuro ADR-006 deben diseñar un bootstrap productivo independiente que cree los canales y configuraciones comerciales propias de Mercadal y re-apunte explícitamente el canal por defecto del store sin recurrir a borrados automáticos. La puesta en marcha de producción queda estrictamente bloqueada hasta la definición de dicha arquitectura, manteniéndose fuera del criterio de cierre funcional de M360-010.
