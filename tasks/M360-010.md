## 6. Lista de Desvíos con Causa

1. **`depends_on` con `condition: service_healthy` vs definiciones preexistentes de Postgres/Redis**:
   - *Causa*: El prompt solicitaba `depends_on` con `condition: service_healthy` para Postgres y Redis, pero las definiciones preexistentes de `mercadal-staging-postgres` y `mercadal-staging-redis` en `docker-compose.staging.yml` no cuentan con bloque `healthcheck:`. Docker Compose prohíbe evaluar `condition: service_healthy` sobre un servicio que carece de bloque de healthcheck (arrojando error fatal `dependency ... has no healthcheck configured`). Dado que el prompt prohíbe explícitamente modificar las definiciones de Postgres/Redis o recrear sus contenedores, se utilizó `depends_on: [mercadal-staging-postgres, mercadal-staging-redis]` (`condition: service_started`), preservando intactos los contenedores de Postgres y Redis (`Up 6 hours`).
2. **Requerimiento de `DATABASE_DRIVER_OPTIONS` para conexión sin TLS en Staging**:
   - *Causa*: Medusa 2.21.2 activa por defecto la negociación TLS/SSL con `rejectUnauthorized: false` para cualquier conexión PostgreSQL cuyo host no sea `localhost` ni `127.0.0.1`. En Staging, la base de datos corre en `mercadal-staging-postgres` (PostgreSQL Alpine sin certificados SSL configurados), lo que provocaba que la conexión de Knex (`verifyMigrationConnection`) quedase en espera del handshake SSL y excediera el timeout de 10 segundos. Se configuró `databaseDriverOptions: process.env.DATABASE_DRIVER_OPTIONS ? JSON.parse(process.env.DATABASE_DRIVER_OPTIONS) : undefined` en `medusa-config.ts` y se suministró `DATABASE_DRIVER_OPTIONS={"connection":{"ssl":false}}` en el `.env.medusa.staging` del VPS, preservando el comportamiento estricto por defecto de producción.
3. **Propiedad de directorios para usuario no-root en migraciones**:
   - *Causa*: Durante la ejecución de migraciones, MikroORM intenta crear la carpeta `dist/migrations` para aquellos módulos que no poseen migraciones preexistentes. Al correr `npm install --omit=dev` como paso de construcción, los directorios de `node_modules` pertenecían inicialmente a root. Se incorporó `chown -R node:node /app/.medusa/server` en la fase de runtime del Dockerfile para que el usuario no-root `node` disponga de los permisos de escritura requeridos.
4. **Reinicio temporal de Postgres/Redis durante prueba del Runbook**:
   - *Causa*: Durante la validación práctica de los comandos del runbook (`infra/staging/README.md`), la ejecución de `docker compose down` detuvo y eliminó temporalmente los contenedores de Postgres y Redis antes de volver a levantarlos con `docker compose up -d`. Si bien los volúmenes persistentes (`mercadal_staging_pgdata` y `mercadal_staging_redisdata`) y la base de datos se mantuvieron 100% íntegros y sin pérdida de datos, el uptime de Postgres y Redis se reseteó a ~20 minutos (en lugar de las 6 horas acumuladas previamente). Se dejó explícitamente documentado en el runbook que para detener únicamente el backend Medusa sin afectar Postgres/Redis debe utilizarse `docker compose stop medusa-api` o `docker compose rm -s -f medusa-api`.
